# ADR 0006 — Utilisateurs, rôles et permissions (RBAC, P2.4)

- **Statut** : acceptée (validation du propriétaire du projet, 08/10/2026)
- **Date** : 08/10/2026
- **Source** : spécification interne non publiée v1.0, §7.1–7.3, §9.12, §14.3 (Role, Permission), §19.1, §24, écrans 23-24 ;
  ADR 0001 (P9, P10), ADR 0005

## Décisions

### 1. Un seul système d'autorisation : `PermissionsMixin` retiré

`User` n'hérite plus de `PermissionsMixin` (migration `users.0003`). Les champs `is_superuser`, `is_staff`, `groups`
et `user_permissions` sont supprimés. Deux raisons : éviter deux systèmes de permissions concurrents, et supprimer
`is_superuser`, qui fait passer `has_perm` pour toute permission, à l'opposé du moindre privilège. `AUTH_USER_MODEL`
est inchangé. La permission Django `organizations.manage_organizations` de P2.3 est remplacée par la permission RBI
`platform.organizations`. `createsuperuser` n'existe plus ; l'amorçage passe par
`manage.py create_super_admin --email …`, avec un mot de passe saisi de façon masquée ou lu sur l'entrée standard.

### 2. Modèle (§14.3)

| Table | Contenu |
|---|---|
| `users_permission` | `code` unique (`module.action`), `module`, `scope` (`platform` / `organization`), description |
| `users_role` | `code`, `scope`, `organization` (NULL pour les rôles par défaut ; rôles personnalisés : V1), `is_system`, `mfa_required` |
| `users_role_permission` | composition d'un rôle, avec la portée du rôle et celle de la permission |
| `users_user_role` | affectation : utilisateur, rôle, portée, organisme de l'utilisateur, auteur, date |

### 3. Catalogue de référence (`apps/users/catalog.py`)

- **28 permissions** (4 plateforme, 24 organisme) et **7 rôles par défaut** : SUPER_ADMIN et AUDITOR (plateforme) ;
  ORG_ADMIN, SUPERVISOR, AGENT, ANALYST et AUDITOR (organisme). Le code d'un rôle est unique par portée (§14.3),
  et le §7.2 F prévoit un auditeur plateforme.
- Les codes reprennent le contrat du frontend P1 (`frontend/src/lib/permissions.ts`), à trois écarts près :
  `users.view` ajouté (lecture des utilisateurs par l'Auditeur, §7.3) ; `platform.audit` remplace `audit.view` pour le
  Super Admin ; `platform.institutional_admins` est ajouté (désignation du premier administrateur, §9.16).
  Le frontend s'alignera en P2.10, lorsque `GET /api/v1/me` fournira la liste effective.
- Le catalogue est synchronisé en base après chaque `migrate` (signal `post_migrate`). La synchronisation est
  idempotente et répare toute modification manuelle des rôles par défaut.
- MFA exigée par rôle (§9.12, §19.1) : SUPER_ADMIN, AUDITOR (les deux portées), ORG_ADMIN, SUPERVISOR.
  Le contrôle à la connexion relève de P2.5 (`rbac.requires_mfa`).

### 4. Séparation des portées garantie par PostgreSQL (migration `users.0004`)

Clés étrangères composites, posées en `RunSQL` et réversibles :
- `(role_id, role_scope) → users_role(id, scope)` et `(permission_id, permission_scope) → users_permission(id, scope)`,
  combinées au `CHECK role_scope = permission_scope` : **un rôle d'organisme ne peut pas contenir une permission
  plateforme**, même par une insertion SQL directe (testé) ;
- `(role_id, scope) → users_role(id, scope)` : la portée d'une affectation est celle du rôle ;
- `(user_id, organization_id) → users_user(id, organization_id)` : une affectation d'organisme porte l'organisme réel de
  l'utilisateur (une affectation dans un autre organisme est rejetée). Un utilisateur ne peut pas changer d'organisme
  tant qu'il détient des rôles.
- Limite : une affectation **plateforme** à un compte organisationnel n'est pas bloquée par la base (`MATCH SIMPLE`
  sur un organisme NULL). Elle est refusée par les services et **ignorée par l'évaluation** (testé).

### 5. Évaluation (`apps/users/rbac.py`) : refus par défaut

`has_permission(user, code, context)` refuse dans les cas suivants : code inconnu ; compte inactif ou anonyme ;
permission plateforme demandée par un compte organisationnel ou dans un contexte d'organisme ; permission d'organisme
sans contexte, ou avec un contexte d'un autre organisme. **Un rôle n'est jamais une preuve d'appartenance** :
l'appartenance vient de `user.organization` et du `TenantContext` déterminé côté serveur. Seules les affectations
cohérentes sont comptées. `require_permission` audite chaque refus, avec un message générique qui ne nomme ni la
permission ni la ressource. `platform_scope` s'appuie sur ce moteur ; `require_scope(scope, permission)` vérifie aussi
la permission pour laquelle le périmètre a été délivré.

### 6. Gestion des utilisateurs (`apps/users/services.py`, §9.12)

- Pas d'auto-inscription. Un compte d'organisme est créé dans l'organisme **du contexte** : aucun paramètre ne permet
  d'en désigner un autre.
- Un Administrateur institutionnel n'attribue que des rôles d'organisme : un code plateforme (`SUPER_ADMIN`) est refusé
  sans rien créer, et `AUDITOR` désigne toujours l'auditeur d'organisme.
- Personne ne peut s'attribuer un rôle ni désactiver son propre compte.
- Le dernier Administrateur institutionnel actif ne peut être ni retiré ni désactivé (écran 24), sous verrou de ligne.
- Un utilisateur d'un autre organisme est indiscernable d'un identifiant inexistant.
- Le Super Administrateur désigne le premier Administrateur institutionnel d'un organisme AUTORISÉ ou ACTIF, avec un
  périmètre délivré pour `platform.institutional_admins`. **L'activation d'un organisme exige désormais un
  Administrateur institutionnel actif.**
- Les comptes créés n'ont pas de mot de passe utilisable : l'invitation sécurisée et l'enrôlement MFA relèvent de P2.5.

## Reporté

- Restriction du Superviseur et de l'Agent à leurs postes d'affectation (P9, `assigned_posts`) : dépend du modèle
  `BorderPost`.
- Activation de `imports.run` pour un Agent ou un Analyste (P10) : rôles personnalisés (V1) ou autorisation ciblée,
  à décider avec le module d'import.
- Rôles personnalisés par organisme (V1), écran 24 en écriture, accès sous mandat (§19.2).
- Classes de permission DRF : avec l'API (P2.8).

## Limites jusqu'à P2.6

Le RLS n'est pas activé. Les tables RBAC (`users_user_role` notamment) et les données organisationnelles restent
lisibles par `rbi_app` au niveau PostgreSQL. Les contrôles RBAC sont applicatifs, à l'exception des contraintes de
portée ci-dessus, qui sont garanties en base.
