# P2.2 — Django + PostgreSQL/PostGIS : rapport

**Date** : 08/10/2026 · Décisions : [ADR 0004](../../adr/0004-socle-django.md) (socle Django) et
[ADR 0003](../../adr/0003-infrastructure-backend.md) (mise à jour PostgreSQL 16.15).

## 1. Objectif

Construire le socle Django réel, connecté à PostgreSQL/PostGIS et à Redis, exécuté dans Docker, sans aucun module métier.

## 2. Analyse

- Spécification interne non publiée : §12.2 (16 applications), §12.3 (contexte organisme côté serveur, RLS `app.current_org`,
  tâches Celery portant l'`organization_id`), §14.2 (UUID v4, timestamptz UTC), §19.1 (secrets dans l'environnement,
  cookies, CSRF), §23 (sondes `/api/v1/health/live` et `/ready`).
- Contraintes P2.1 à préserver : rôle applicatif non propriétaire et soumis au RLS, superutilisateur jamais transmis
  au backend, tout lancé dans Docker.
- Deux décisions ne peuvent pas attendre les sous-phases suivantes : `AUTH_USER_MODEL` (immuable après la première
  migration) et le choix du rôle PostgreSQL par service.
- PostgreSQL : **16.15** est la dernière mineure de la branche 16 (13/08/2026, d'après postgresql.org) ; P2.1 utilisait 16.14.

## 3. Architecture retenue

```
docker compose up -d --wait
  db, redis, storage, mailpit   (P2.1)
  migrate  ──(rbi_owner)──► migrations, puis s'arrête
  api      ──(rbi_app)────► check_db_role → runserver :8000   (/api/v1/health/live|ready)
  worker   ──(rbi_app)────► check_db_role → celery worker      (tâche health.ping)
  backend  (profil tools, rbi_owner) : pytest (base test_rbi), ruff, mypy
```

Projet `config/` (settings `base`/`development`/`test`, `env.py`, `celery.py`, urls, wsgi/asgi) et 16 applications
`apps/<nom>` enregistrées. Contenu en P2.2 : `core` (modèles abstraits UUID/horodatage, commande `check_db_role`),
`health` (sondes, tâche `ping`), `users` (modèle utilisateur technique). Les 13 autres ne contiennent que leur `AppConfig`.

## 5. Configuration

- Toutes les valeurs viennent de l'environnement (`config/env.py`). Secrets sans valeur par défaut : une variable
  obligatoire absente arrête le démarrage avec son **nom** (jamais sa valeur).
- `base.py` est sûr par défaut : `RBI_ENV=production`, `DEBUG=False`, `ALLOWED_HOSTS=[]`, cookies `Secure` + `HttpOnly`
  + `SameSite=Strict`, `nosniff`, `X-Frame-Options: DENY`. `development.py` assouplit uniquement pour HTTP local ;
  `test.py` ajoute `tests.gisprobe` et la base `test_rbi`.
- Variables ajoutées : `RBI_DJANGO_SECRET_KEY` (générée), `RBI_API_HOST_PORT`. `py scripts/init_env.py` complète désormais
  un `.env` existant sans toucher aux secrets en place (exécuté : 2 variables ajoutées, aucune modifiée).

## 6. Migrations

- `users.0001_initial` (User : UUID, e-mail unique, `PermissionsMixin`) avec les migrations `contenttypes` et `auth`,
  appliquées par le service `migrate` sous `rbi_owner` : 15 migrations, toutes OK.
- `gisprobe.0001_initial` n'existe que dans la base de test (absence vérifiée dans la base de développement).
- `makemigrations --check` : aucune migration manquante (test automatisé).
- Base de développement après migration : 8 tables, **toutes propriété de `rbi_owner`** ; `rbi_app` ne possède aucune table.

## 7. PostgreSQL / PostGIS

- **16.14 → 16.15** : image reconstruite, **volume `rbi_pgdata` conservé** (date de création inchangée, initialisation non
  rejouée). Procédure documentée dans l'ADR 0003 ; aucune recréation nécessaire pour une version mineure.
- Pilote **psycopg 3.3.6** confirmé (`is_psycopg3`, `connection.Database` = `psycopg`) ; moteur GeoDjango PostGIS.
- Vérifié par tests : PostgreSQL 16, extension PostGIS 3.x, écriture/lecture d'un `PointField(geography=True)` et d'un
  `PolygonField`, distance géodésique (110 574 m pour 1° de latitude), `dwithin`, `contains`, `ST_Transform` vers
  EPSG:3857, `AsGeoJSON`. Coordonnées fictives uniquement.

## 8. Redis

Cache Django (base 2), broker Celery (base 0), résultats (base 1). Tests : aller-retour du cache, connexion au broker,
**aller-retour réel `health.ping` par le worker** (« pong »). Celery n'accepte que JSON.

## 9. Sécurité

- Aucun secret dans le code ni dans Git ; `.env` ignoré (`git check-ignore`) ; recherche des valeurs du `.env` dans
  l'arbre de travail : aucune occurrence hors `.env`.
- Séparation des rôles respectée : `migrate` et tests en `rbi_owner`, `api` et `worker` en `rbi_app` ; aucune élévation de privilège.
- **Garde-fou nouveau** : `check_db_role` empêche l'API et le worker de démarrer avec un rôle superutilisateur, BYPASSRLS,
  propriétaire ou membre d'un rôle. Testé : accepte `rbi_app`, refuse `rbi_owner` sans divulguer de mot de passe.
- `/ready` ne renvoie que `ok`/`error` ; testé avec une erreur contenant un faux mot de passe, qui n'apparaît pas dans la réponse.
- Celery sans pickle. `pip-audit` : 0 vulnérabilité connue.

## 12. Problèmes rencontrés

1. L'API renvoyait 500 : `AuthenticationMiddleware` exige le middleware de sessions.
2. Test `ST_Transform` en échec : la fonction n'accepte pas le type `geography`.
3. Test des réglages en échec : pytest-django remplace le nom de base par `test_rbi` dans le processus de test.
4. **Fuite de connexions** : 34 connexions `rbi-api` inactives (serveur de développement multithread + `CONN_MAX_AGE=60`) ;
   à terme, épuisement de `max_connections`.
5. Le test qui identifiait le rôle de l'API via `pg_stat_activity` dépendait de cette connexion persistante.
6. mypy : décorateur Celery non typé, attributs propres à PostgreSQL et PostGIS ; ruff : migrations générées, lignes longues.

## 13. Solutions

1. Middleware d'authentification retiré jusqu'à P2.5 (sessions et authentification y seront configurées ensemble).
2. Conversion explicite `Cast(..., GeometryField)` avant `Transform` ; règle consignée dans l'ADR 0004.
3. Réglages vérifiés dans un processus neuf.
4. `CONN_MAX_AGE=0` en développement ; persistance conservée par défaut pour un serveur WSGI.
5. Remplacé par le garde-fou `check_db_role`, plus fort : il bloque le démarrage au lieu d'observer après coup.
6. `celery-types`, `cast` documenté dans les tests, migrations exclues de ruff, lignes repliées.

## 14. Limites restantes

- Serveur de développement Django uniquement ; serveur WSGI et `settings/production.py` arriveront avec le déploiement.
- Pas encore de DRF/OpenAPI (P2.8), de sessions/authentification (P2.5), de Celery Beat (première tâche planifiée).
- Les tests Django tournent avec `rbi_owner` sur `test_rbi`. Pour P2.6, une seconde connexion de test sous `rbi_app`
  sera nécessaire afin que les tests d'isolation soient réellement soumis au RLS.
- 13 applications sont des coquilles (`AppConfig` seulement), par choix.

## 15. Impact sur P2.3

- `TimestampedModel` (UUID v4 + horodatages) sert de base aux modèles `Organization` et aux modèles organisationnels.
- Le rattachement `User → Organization` s'ajoute par une migration de `users` ; aucun changement de `AUTH_USER_MODEL`.
- L'organisme se déduira de `request.user` côté serveur ; le middleware de contexte pourra s'appuyer sur la transaction
  par requête qui accueillera `SET LOCAL app.current_org` (P2.6).
- `check_db_role` garantit déjà que l'API tournera sous un rôle soumis aux politiques RLS de P2.6.
