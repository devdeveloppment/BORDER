# P2.7 — Journal d'audit sécurisé et append-only : rapport

Décisions détaillées : [ADR 0009](../../adr/0009-journal-audit-append-only.md).

## 1. Objectif

Remplacer le journal applicatif (lignes JSON sur `rbi.audit`) par un journal **conservé dans PostgreSQL**, en
**insertion seule**, **chaîné** par SHA-256, cloisonné par organisme et compatible avec le RLS de P2.6
(§9.11, §14, §19.1, écran 22).

## 2. Audit préalable (état réel en début de sous-phase, arbre propre)

- **Producteurs** : 47 appels à `record_event` dans 6 fichiers (authentification, MFA, sessions, RBAC, périmètre
  plateforme, cycle de vie des organismes, comptes et rôles). Aucun ne déterminait l'objet de façon structurée
  (`target` texte libre) ; plusieurs refus étaient émis **dans** une transaction annulée ensuite (ils auraient été
  perdus avec une écriture en base naïve).
- **Consommateurs** : 4 fichiers de tests relisaient le journal technique (`caplog`) ; aucune lecture en base.
- **Manques** : aucune table, aucun identifiant de requête, aucune adresse IP, aucun refus de contexte d'organisme
  journalisé, aucun chemin de consultation.
- **Spécification interne non publiée** : table append-only « protection par droits PostgreSQL et chaînage d'empreintes »,
  INSERT et SELECT seulement pour le rôle applicatif, champs du §14, indicateur d'intégrité (écran 22),
  conservation selon la politique de l'organisme. Ce qui est exigé et ce qui est proposé en plus : ADR 0009,
  tableau « Exigé ou proposé ».

## 3. Réalisé

- **Table `audit_auditlog`** (SQL, migration `audit.0001_initial`) : champs du §14 + portée, type d'acteur,
  résultat, métadonnées ; contraintes de forme ; pas de clé étrangère (justifié dans l'ADR). **Table `audit_chain`**
  (têtes de chaîne).
- **Scellement par PostgreSQL** (déclencheur `SECURITY DEFINER`) : identifiant, horodatage UTC, `prev_hash`, `hash`
  posés par la base sous verrou de la tête de chaîne ; une chaîne par organisme et une chaîne plateforme.
- **Append-only** : privilèges (INSERT de 13 colonnes, SELECT ; rien d'autre), déclencheurs d'immuabilité (UPDATE,
  DELETE, TRUNCATE refusés même au propriétaire tant qu'il ne les désactive pas), modèle Django en lecture seule,
  retour arrière de migration refusé tant que le journal contient des entrées.
- **RLS** : attribution limitée au contexte serveur (organisme du contexte, du compte du périmètre, ou opération
  plateforme délivrée) ; lecture avec `audit.view` / `platform.audit` **revérifiée en SQL** par deux fonctions
  `SECURITY DEFINER`.
- **Écriture** (`apps/audit/services.py`, `writer.py`) : catalogue fermé de 39 actions, validation anti-secrets,
  contexte serveur capturé ; refus et échecs écrits immédiatement sur une connexion dédiée en `rbi_app`, succès
  après COMMIT.
- **Contexte de requête** (`apps/core/request_context.py`) : identifiant de requête généré par le serveur
  (`X-Request-ID` renvoyé, valeur du client ignorée), IP du pair TCP (désactivable).
- **Producteurs adaptés** : objet structuré, ancienne / nouvelle valeur (statut d'organisme, champs modifiés,
  rôles, activation), actions système explicites ; refus RBAC rattaché à l'organisme de l'acteur ; refus de
  contexte d'organisme désormais journalisé (`tenant.access`).
- **Consultation et intégrité** (`selectors.py`, `integrity.py`) : lecture de son organisme ou de la plateforme,
  vérification de chaîne recalculée en Python ; chaque consultation et vérification est journalisée ; commande de
  maintenance `audit_verify` (toutes les chaînes, têtes à ancrer, code de sortie non nul si altération).
- **Contrôle système** `rbi.E001` : mode d'écriture `inline` interdit hors tests.

## 5. Migrations et compatibilité

- `audit.0001_initial` dépend de `core.0001_row_level_security` (fonctions de périmètre) ; exécutée par le rôle
  propriétaire ; réversible (testé dans `test_p23_to_p27_migrations_are_reversible`, avec la décision explicite
  `rbi.audit_allow_drop`), retour arrière refusé sans elle (testé).
- Aucun privilège supplémentaire pour `rbi_app` hors du journal ; aucune modification des politiques P2.6.
- `makemigrations --check` : aucun écart.
- **Base de développement** : la migration y a été appliquée pendant le développement (le service `migrate` se
  lance avant chaque `docker compose run backend`), avec une version intermédiaire du déclencheur de scellement.
  La fonction a été remplacée par sa version finale (`CREATE OR REPLACE`, rôle propriétaire), sans retour arrière
  ni perte d'entrées ; volumes conservés.

## 7. Problèmes rencontrés

- **Tri lexicographique dans le vérificateur** : la requête sélectionnait `id::text` puis `ORDER BY id`, que
  PostgreSQL résout sur la colonne de sortie texte (« 102 » < « 11 » < « 5 »). Invisible sur de petites chaînes,
  révélé par le test de concurrence ; corrigé (`ORDER BY audit_auditlog.id`) et couvert par une contre-épreuve.
- **Ordre déclencheur / contraintes** : le déclencheur `BEFORE INSERT` précède les contraintes CHECK ; un événement
  d'organisme sans organisme produisait une erreur trompeuse (clé de chaîne nulle). Refus explicite ajouté.
- **Ordre du retour arrière** : la garde de destruction devait être la dernière opération de la migration pour
  s'exécuter en premier au retour arrière.
- **Connexion d'écriture par thread** : laissée au ramasse-miettes avec un serveur à threads éphémères ; fermée
  désormais en fin de requête (testé).
- **Migration appliquée en développement avant sa version finale** : voir §5.
- **Motif libre sans longueur maximale** : un motif de plus de 200 caractères aurait fait échouer une suspension
  par une erreur d'audit obscure. Le motif est désormais limité à 500 caractères avec un message clair (testé),
  et l'audit accepte 500 caractères.

## 8. Limites connues et risques non résolus

Voir ADR 0009, « Limites ». En résumé : le chaînage **détecte** mais ne rend pas le journal **inviolable** — un
propriétaire ou superutilisateur peut tout réécrire et recalculer, ce que seul un ancrage externe révélerait ; une
injection SQL sous `rbi_app` pourrait insérer des entrées falsifiées (sans pouvoir modifier ni supprimer) ; un
succès peut être perdu entre COMMIT et écriture lors d'un arrêt brutal ; les valeurs secrètes sous une clé neutre
ne sont pas détectables automatiquement ; une chaîne sérialise les écritures d'audit d'un organisme ; rétention non
implémentée ; IP enregistrée par défaut sur données fictives, à valider juridiquement.

## 9. Adaptations pour P2.8 et P2.10

- P2.8 : exposer `list_organization_events` / `list_platform_events` / `verify_*_chain` (écran 22 : filtres,
  pagination par `before_id`, export journalisé) ; déclarer `audit.export` avec l'export.
- P2.10 : derrière Nginx, déclarer le proxy de confiance avant de lire l'IP cliente ; l'en-tête `X-Request-ID`
  peut être affiché dans les messages d'erreur pour le support.
