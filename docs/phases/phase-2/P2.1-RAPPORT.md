# P2.1 — Infrastructure et environnement backend : rapport

**Date** : 08/10/2026 · **Périmètre** : environnement Docker Compose, image backend, rôles PostgreSQL, tests d'infrastructure.
Aucun code Django, aucune modification du frontend. Décisions détaillées : [ADR 0003](../../adr/0003-infrastructure-backend.md).

## 1. Analyse

- Spécification interne non publiée v1.0 : §12 architecture et isolation à 5 niveaux, §13 technologies,
  §14.2 conventions, §19 sécurité, §23 supervision (`/api/v1/health/live|ready`), §24 tests, §25 environnements.
- ADR 0001 (Docker Compose, RLS dès P2, Mailpit) et ADR 0002 ; rapport P1.
- Environnement de référence : Docker Desktop (Compose v2, WSL 2) ; Python hôte non utilisé par le backend (qui tourne en conteneur) ; **port 5432 occupé** par une instance PostgreSQL locale.
- Constats : **MinIO n'est plus distribué** (dépôt archivé, images retirées) ; `postgis/postgis:16-3.5` embarque PostgreSQL 16.9 sur Debian 11.

## 4. Commandes

```bash
py scripts/init_env.py                                           # une fois : .env aléatoire
docker compose up -d --wait                                      # démarrer
docker compose ps                                                # état et santé
docker compose --profile tools run --rm backend pytest -m infra  # tests
docker compose stop        # arrêter (conteneurs conservés)
docker compose down        # arrêter et supprimer les conteneurs (données conservées)
docker compose down -v     # tout supprimer, volumes compris (réinitialisation complète)
```

| Contrôle | Résultat |
|---|---|
| `docker compose config -q` | OK |

| `pytest -m infra` (dans le conteneur backend) | **21 / 21 réussis** |

Ce que les 21 tests démontrent : PostgreSQL 16 + PostGIS opérationnel, encodage UTF-8, fuseau UTC, scram-sha-256 ;
`rbi_app` sans aucun privilège d'administration ni appartenance de rôle, `rbi_owner` non superutilisateur, base possédée
par `rbi_owner` ; le backend ne reçoit pas le mot de passe superutilisateur ; `rbi_app` ne peut rien créer ni se connecter
à `postgres` ; **RLS réel** sur table temporaire (0 ligne sans contexte, filtrage par organisme, `WITH CHECK` refusant
l'écriture pour un autre organisme, contexte effacé en fin de transaction, impossibilité de désactiver le RLS, de supprimer
ou de vider la table) ; le propriétaire crée une base de test qui contient PostGIS ; Redis 7 avec authentification
obligatoire, AOF et `noeviction` ; S3 : aller-retour d'objet, URL présignée, 403 anonyme, refus de mauvais identifiants ;
Mailpit capture un e-mail envoyé en SMTP ; image : Python ≥ 3.12, versions de la stack, GDAL/GEOS chargés par GeoDjango
avec reprojection 4326 → 3857 correcte, exécution sans root.

## 6. Problèmes rencontrés et solutions

1. **MinIO indisponible** : remplacé par SeaweedFS (Apache-2.0), après vérification que l'authentification S3 est imposée. Écart à valider (ADR 0003 §4).
2. **Image PostGIS obsolète** (PG 16.9 / Debian 11) : image construite sur `postgres:16.14-trixie` + PostGIS PGDG.
3. **Port 5432 occupé** : PostgreSQL publié sur 5433 (configurable).
4. **Échec d'initialisation avec `--auth-local=peer`** : l'amorçage se connecte par socket sous un autre nom ; option retirée.
   Le redémarrage automatique avait réutilisé le volume à moitié initialisé : volume recréé (`down -v`), procédure documentée.
5. **DRF 3.16.1 vulnérable** (CVE-2026-73228, CVE-2026-73229) : contrainte `>=3.17.2,<3.18`.
6. **Valeur attendue erronée dans un test** (reprojection : 261 600,80 m et non 261 600) : assertion corrigée avec tolérance.
7. Ruff (longueurs de ligne, `noqa` mal placé) et mypy (typage de redis-py) : corrigés.

## 7. Limites assumées

- Pas de serveur applicatif, de worker ni de Beat : il n'existe encore aucun code à exécuter.
- SeaweedFS en mode `mini` est réservé au développement et à la démonstration ; la production exigera TLS et identités IAM dédiées.
- Le RLS métier (politiques par table, contexte posé par middleware et tâches Celery) est l'objet de P2.6 ; P2.1 n'en valide que les prérequis.
