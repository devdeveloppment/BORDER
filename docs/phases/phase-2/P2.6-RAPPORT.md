# P2.6 — Row-Level Security PostgreSQL : rapport

**Date** : 08/10/2026 · Décisions : [ADR 0008](../../adr/0008-row-level-security.md) · Point de départ : fin de P2.5.

## 1. Objectif

Isoler les organismes **dans PostgreSQL** : un accès SQL direct sous `rbi_app` ne doit permettre ni de lire, ni de
modifier, ni de supprimer, ni de créer des données d'un autre organisme, même en cas d'oubli de filtre ORM, de SQL
brut, de `_base_manager`, de tâche sans contexte, de contexte absent, périmé ou mal formé, d'identifiant falsifié ou
de transaction précédente.

## 2. Audit initial (état réel avant P2.6)

17 tables dans `public`, **aucune avec RLS**, aucune politique, aucune fonction `SECURITY DEFINER`. `rbi_app` avait
SELECT/INSERT/UPDATE/DELETE sur toutes les tables (pas TRUNCATE). Rôles sains : `rbi_app` ni superutilisateur, ni
BYPASSRLS, ni membre d'un rôle. Contexte d'organisme purement applicatif (`ContextVar`), jamais transmis à PostgreSQL.

## 4. Réalisé

- **Mécanisme de contexte** (`apps/core/db_scope.py`) : `app.current_org`, `app.current_user`, `app.auth_email` et
  `app.platform`, posés par `set_config(..., true)` dans une transaction ou un point de sauvegarde, avec restauration
  exacte en sortie.
- **Raccordement** :
  - `tenant_context` (requêtes, tâches) ;
  - middleware : chaque requête authentifiée s'exécute dans son périmètre et dans une transaction ;
  - `@platform_operation` (opérations globales) et `@organization_operation` (administration d'un organisme) ;
  - `identity_scope` : backend d'authentification, étape MFA, jetons de réinitialisation, lectures RBAC et MFA.
- **Migration RLS** : 9 tables protégées, 19 politiques, privilèges réduits, 3 fonctions `SECURITY DEFINER`
  bornées, 4 fonctions de lecture du périmètre.
- **Défauts applicatifs révélés par le RLS et corrigés** :
  - `SELECT … FOR UPDATE` joint qui verrouillait aussi le catalogue (`of=("self",)`) ;
  - mise à jour d'une ligne invisible dans le périmètre : désormais refusée explicitement, au lieu du repli de Django
    vers un INSERT ;
  - évaluation MFA hors périmètre : elle aurait conclu « pas de MFA » (échec permissif).
- **Maintenance** : `create_super_admin` et `reset_user_mfa` refusent de s'exécuter sous `rbi_app`.
- **Réinitialisation MFA par un administrateur** : par fonction SQL, sans que le rôle applicatif puisse lire les
  secrets d'autrui.
- **Tests** : le corps de chaque test s'exécute en `rbi_app`. L'inventaire versionné est confronté à PostgreSQL, et
  toute table nouvelle ou non protégée fait échouer la suite.

Couverture des exigences :
- **A. SQL direct sous `rbi_app`** :
  - A ne lit que ses lignes ;
  - A ne peut pas modifier ni supprimer les lignes de B (0 ligne affectée), ni créer pour B, ni transférer une ligne
    vers B (violation RLS) ;
  - sans contexte : 0 ligne visible sur 8 tables et écritures refusées ; contexte inconnu : 0 ligne ;
  - contexte mal formé, y compris une tentative d'injection : erreur de conversion UUID, aucun accès ;
  - désactiver ou supprimer une politique, en créer une ouverte, changer de propriétaire, TRUNCATE, CREATE TABLE,
    ALTER ROLE BYPASSRLS ou SUPERUSER : refusés ; GRANT sans effet ;
  - affectations de rôles, catalogue en lecture seule, demandes d'accès, secrets MFA du seul titulaire (pas même
    l'administrateur du même organisme) ;
  - recherche de connexion limitée au compte recherché ;
  - fonctions `SECURITY DEFINER` bornées.
- **B. Contexte et transactions**, sur de vraies connexions `session_user = rbi_app` :
  - contexte effacé après commit, après rollback et après une transaction échouée ;
  - connexion réutilisée A → B → A sans fuite ; `SET LOCAL` hors transaction sans effet ;
  - `SET ROLE` vers le propriétaire et `SET SESSION AUTHORIZATION` refusés ;
  - côté Django : périmètres imbriqués restaurés, restauration après exception et après erreur SQL, valeurs passées
    en paramètres ; aucun contexte résiduel après des requêtes HTTP successives de A puis B sur la même connexion.
- **C. HTTP et RBAC** : tous les parcours P2.5 (connexion, MFA, réinitialisation, sessions) s'exécutent sous RLS ;
  identifiants falsifiés sans effet ; limites des rôles P2.4 inchangées ; aucune fuite de secret dans les réponses et
  journaux (tests P2.5 rejoués).
- **D. Tâches** : tâche sans `organization_id` ou avec un organisme inconnu refusée ; tâches A puis B isolées en SQL
  brut ; échec en cours de tâche annulé sans contaminer la suivante.

## 8. Problèmes rencontrés

1. **Migration RLS non appliquée au premier essai** : `apps/core/migrations/__init__.py` manquait, et 63 tests
   passaient alors **sans protection**. Détecté par l'échec d'un appel à une fonction SQL absente, puis corrigé. Le test
   d'inventaire empêche désormais qu'une telle situation passe inaperçue.
2. **Politique récursive** (`users_user` interrogeant `users_user`) : remplacée par `rbi_current_user_org()`.
3. **Défauts applicatifs révélés sous RLS** : verrou joint, mise à jour d'une ligne invisible, évaluation MFA hors
   périmètre (§4).
4. **Harnais de test** : `SET ROLE` vers le propriétaire et `SET ROLE NONE` réussissent quand la session appartient
   au propriétaire. Ces cas sont testés sur de vraies connexions `rbi_app`.
5. **`set_config(…, true)` dans un point de sauvegarde survit jusqu'à la fin de la transaction englobante** : c'est le
   comportement de PostgreSQL, et la raison de la restauration explicite dans `db_scope`. Un test erroné a été corrigé.
6. **Installation depuis zéro en échec au premier essai** : image PostgreSQL non reconstruite après la modification du
   script initdb. Image reconstruite, puis 342 tests verts.

## 9. Limites connues et risques non résolus

- **Injection SQL** : les variables de contexte peuvent être redéfinies par quiconque exécute du SQL arbitraire sous
  `rbi_app`. Le RLS protège contre les oublis et les chemins sans contexte, pas contre une injection, qui reste
  prévenue par l'ORM et les requêtes paramétrées.
- **Propriétaire hors RLS** (pas de FORCE), compensé par `check_db_role`, la séparation des identifiants et les gardes
  de maintenance.
- **Contraintes d'unicité globales** (e-mail) : elles peuvent révéler l'existence d'une valeur dans un autre organisme.
- **Visibilité interne** : tout membre d'un organisme voit en SQL les comptes et affectations de son organisme.
- **Secrets TOTP en clair** (non traité) ; **sessions** dans Redis, hors RLS ; **audit** non encore append-only (P2.7).

## 10. Adaptations pour P2.10

- Le frontend n'est pas concerné par le RLS : le contrat HTTP est inchangé.
- Toute nouvelle vue métier hérite du périmètre du middleware. Toute nouvelle table doit être ajoutée à l'inventaire
  avec sa politique, sinon les tests échouent.
- Derrière Nginx, aucun impact sur le contexte, qui ne vient jamais d'un en-tête.
