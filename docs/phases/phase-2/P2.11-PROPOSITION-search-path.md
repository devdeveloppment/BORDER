# Proposition — `search_path` des fonctions `SECURITY DEFINER` (défaut découvert en P2.11)

**Statut : appliquée en développement le 12/10/2026** (migration `core.0003_definer_search_path`),
sur autorisation distincte du propriétaire ; voir §8. Les sections 1 à 7 sont la proposition telle que revue avant
application (option 1 retenue sans modification).

## 1. Défaut

Les fonctions `SECURITY DEFINER` du projet fixent `search_path = pg_catalog, public` et nomment leurs tables sans
schéma. PostgreSQL parcourt alors **d'abord le schéma temporaire de la session** (`pg_temp`) pour résoudre une table,
sauf si `pg_temp` est placé explicitement dans la liste. Les fonctions, elles, ne sont jamais résolues dans `pg_temp`.

Or le rôle applicatif peut créer des tables temporaires (`GRANT CONNECT, TEMPORARY ON DATABASE … TO rbi_app`,
`infra/postgres/initdb/10-rbi-init.sh`). Une session qui exécute du SQL arbitraire sous `rbi_app` peut donc créer
une table temporaire homonyme (par exemple `users_user`), y accorder `SELECT` au propriétaire, et faire lire ses
propres lignes par la fonction exécutée avec les droits du propriétaire.

**Démonstration** (PostgreSQL 16 jetable, sans réseau, réplique minimale, données fictives ; jamais sur la base
réelle) : avec le `search_path` actuel, `rbi_audit_platform_reader()` renvoie vrai pour un compte **inexistant** et
3 lignes du journal plateforme deviennent lisibles ; avec `pg_catalog, public, pg_temp`, la même attaque renvoie faux
et 0 ligne.

**Condition préalable** : exécuter du SQL arbitraire sous `rbi_app` (injection SQL, identifiants de base dérobés).
Dans ce cas, l'attaquant peut déjà poser les variables de périmètre (`app.current_user`, `app.platform`) ; le masquage
supprime en plus le besoin de connaître un compte réel, actif et doté de la permission. **Défense en profondeur ;
gravité moyenne.** À signaler au test d'intrusion indépendant.

Non concernées : `rbi_audit_immutable()` (invocateur ; ne lit aucune table), `rbi_audit_digest`,
`rbi_audit_netstring`, `rbi_audit_json_safe` (invocateur, sans table), `rbi_current_user`, `rbi_current_org`,
`rbi_platform`, `rbi_auth_email` (invocateur, lecture de variables de session).

**Exécution et dépendances (rectifié le 12/10/2026, addendum de revue finale)** :

- Huit fonctions `SECURITY DEFINER`, toutes dans le schéma `public`, propriétaire `rbi_owner`. **Sept** sont
  exécutables directement par `rbi_app` (droit `EXECUTE`) ; la huitième, `rbi_audit_seal()`, n'a `EXECUTE` que pour
  `rbi_owner` : c'est la fonction du déclencheur `rbi_audit_seal` (`BEFORE INSERT` sur `audit_auditlog`). Le droit
  `EXECUTE` n'est vérifié qu'à la création d'un déclencheur : chaque insertion de `rbi_app` dans le journal l'exécute
  donc, et elle reste dans le périmètre du défaut.
- Politiques RLS : 22 politiques appellent des fonctions `rbi_`, mais surtout les fonctions invocatrices sans table
  (`rbi_current_org`, `rbi_platform`, `rbi_current_user`, `rbi_auth_email`). **Quatre seulement** appellent une
  fonction `SECURITY DEFINER` : `users_user.rbi_user_update` et `audit_auditlog.rbi_audit_insert`
  (`rbi_current_user_org`), `audit_auditlog.rbi_audit_select` et `audit_chain.rbi_audit_chain_select`
  (`rbi_audit_org_reader`, `rbi_audit_platform_reader`). L'affirmation antérieure « 22 politiques RLS appellent ces
  fonctions » était inexacte.
- Conséquence inchangée : une erreur de remédiation bloquerait l'écriture et la lecture du journal d'audit et la mise à
  jour des comptes, d'où les tests ci-dessous.

Définitions actuelles : `core.0001_row_level_security` (`rbi_current_user_org`, `rbi_org_has_active_admin`,
`rbi_admin_reset_mfa`), `core.0002_api_read_functions` (`rbi_org_mfa_enabled_users`, `rbi_platform_org_user_counts`),
`audit.0001_initial` (`rbi_audit_seal`, `rbi_audit_org_reader`, `rbi_audit_platform_reader`).

## 3. Stratégie proposée

1. **Option retenue — `search_path` sûr** : `ALTER FUNCTION … SET search_path = pg_catalog, public, pg_temp;` pour
   les huit fonctions. `pg_temp` en dernier : une table temporaire ne peut plus masquer une table de `public`.
   Recommandation de la documentation PostgreSQL (« Writing SECURITY DEFINER Functions Safely »). Aucun changement de
   corps, de signature, de propriétaire ni de privilège.
2. **Renfort facultatif** : qualifier toutes les références (`public.users_user`, `public.rbi_current_user()`) lors
   de la prochaine réécriture de chaque fonction. Plus intrusif (réécriture des corps) ; non nécessaire si 1 est
   appliqué.
3. **Option écartée pour ce lot — `REVOKE TEMPORARY … FROM rbi_app`** : supprime la cause, mais c'est une modification
   de privilège de base de données dont l'effet sur Django, psycopg et les outils doit être évalué séparément.

## 4. Compatibilité

- `ALTER FUNCTION … SET search_path` ne change ni le résultat ni les droits pour un appel légitime (aucune table
  temporaire homonyme n'existe en exploitation) ; il ne réécrit pas la fonction.
- `CREATE OR REPLACE FUNCTION` d'une migration ultérieure **réinitialiserait** la configuration si elle omet la clause
  `SET` : ajouter un test qui vérifie `proconfig` de chaque fonction `SECURITY DEFINER` (garde de non-régression).
- Coût : nul à l'exécution (la clause `SET` existe déjà).

## 5. Migration réversible (projet, non créée)

```python
FUNCTIONS = (
    "rbi_admin_reset_mfa(uuid)", "rbi_audit_seal()", "rbi_audit_org_reader()", "rbi_audit_platform_reader()",
    "rbi_current_user_org()", "rbi_org_has_active_admin(uuid)", "rbi_org_mfa_enabled_users()",
    "rbi_platform_org_user_counts()",
)
FORWARD = "".join(f"ALTER FUNCTION {f} SET search_path = pg_catalog, public, pg_temp;\n" for f in FUNCTIONS)
REVERSE = "".join(f"ALTER FUNCTION {f} SET search_path = pg_catalog, public;\n" for f in FUNCTIONS)
operations = [migrations.RunSQL(FORWARD, REVERSE)]
```

## 6. Tests prévus

1. Pour chaque fonction : `prosecdef` vrai et `proconfig = {search_path=pg_catalog, public, pg_temp}` ; toute nouvelle
   fonction `SECURITY DEFINER` sans cette configuration fait échouer le test. Le test porte sur **toutes** les
   fonctions `SECURITY DEFINER` (huit), pas seulement sur celles qu'exécute `rbi_app` (sept, liste figée par
   `test_no_sql_function_privilege_or_policy_is_added`).
2. Usurpation par tables temporaires, **dans la base de test jetable** : sous `rbi_app`, tables temporaires homonymes
   (`users_user`, `users_user_role`, `users_role`, `users_role_permission`, `users_permission`, `audit_chain`) remplies
   et ouvertes au propriétaire ; chaque garde doit refuser (lecteurs d'audit faux, 42501 pour les fonctions de
   lecture, aucune MFA supprimée, tête de chaîne réelle avancée et chaîne intacte).
3. Suite complète inchangée : les quatre politiques qui appellent une fonction `SECURITY DEFINER`, le déclencheur
   `rbi_audit_seal` et, plus largement, les 22 politiques RLS continuent de fonctionner.
4. Contre-épreuve : retirer `pg_temp` d'une fonction fait échouer le test 2 correspondant.

## 7. Ordre de déploiement et retour arrière

1. Environnement jetable : suite complète, tests d'usurpation, contre-épreuves.
2. Développement : sauvegarde logique préalable, application de la migration, `audit_verify`, parcours de connexion
   et MFA, export du journal.
3. Pilote : uniquement après le test d'intrusion indépendant.

**Retour arrière** si : une politique RLS échoue (erreur 42501 ou 42P01 inattendue), un test de la suite régresse, ou
la vérification de la chaîne d'audit signale une anomalie. La migration inverse rétablit l'état antérieur exact
(`search_path = pg_catalog, public`) ; aucune donnée n'est modifiée dans un sens ni dans l'autre.

**Risque** : le défaut `search_path` est **corrigé en développement**. Il reste à le vérifier par le test
d'intrusion indépendant et à appliquer la migration à tout autre environnement, qui n'a pas été ciblé.
