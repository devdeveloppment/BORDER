# P2.3 — Organisations et fondations du multi-tenant : rapport

**Date** : 08/10/2026 · Décisions : [ADR 0005](../../adr/0005-organismes-multi-tenant.md).

## 1. Objectif

Modèle Organisation, cycle de vie institutionnel et fondations de l'isolation entre organismes : contexte déterminé
côté serveur, fermé par défaut, refus des accès inter-organismes, opérations globales réservées et auditées.

## 2. Analyse

Relu : spécification interne non publiée §2.3, §7.1–7.3, §8.3, §9.16, §12.3, §14.2–14.3 (Organization, OrganizationAuthorization,
User, DataSource), §20, écrans 5 et 31 ; ADR 0001–0004 ; rapports P2.1/P2.2 ; contrat frontend P1 (`types.ts`, mêmes
valeurs d'énumération : `EN_ATTENTE`… `ARCHIVEE`, `douane`… `autre`, `mutualise`/`dedie`).

## 3. Réalisé

- **Organisation** (`Organization`), **autorisation formelle** (`OrganizationAuthorization`), **demande d'accès**
  (`AccessRequest`), avec contraintes en base (CHECK, unicités insensibles à la casse, période valide, consentement).
- **Cycle de vie** : enregistrement (EN_ATTENTE), autorisation (AUTORISÉE), activation (ACTIVE, autorisation en vigueur
  exigée), suspension/réactivation (motif obligatoire), archivage définitif ; rejet ou traitement d'une demande d'accès.
- **Utilisateur** : `User.organization` (NULL uniquement pour les comptes plateforme), sans changer `AUTH_USER_MODEL`.
- **Source de données** : `DataSource`, première donnée organisationnelle, distincte de l'organisme et des utilisateurs.
- **Multi-tenant** : `TenantContext` + `ContextVar`, `TenantScopedModel` + `TenantManager` fermés par défaut,
  `TenantContextMiddleware` (source unique : `request.user`), `@tenant_task` pour Celery.
- **Opérations globales** : `platform_scope` (compte plateforme + permission `manage_organizations`, audité) et
  `require_scope` en tête de chaque service global.
- **Audit** : `apps.audit.services.record_event` (journal `rbi.audit` en JSON ; persistance append-only en P2.7).

## 7. Problèmes rencontrés et solutions

1. `Meta` interne ne voit pas les énumérations de la classe englobante : énumérations au niveau du module, alias conservés.
2. Un service global appelé avec un `User` n'échouait qu'**après** l'écriture (annulée par la transaction) : ajout de
   `require_scope` en entrée de chaque service et sélecteur global.
3. Le paramètre `timezone` de `register_organization` masquait `django.utils.timezone` : import renommé.
4. `activate` / `reactivate` vérifiaient le statut sur l'objet en mémoire : vérification déplacée sur la ligne verrouillée.
5. `TGO` rejeté par `varchar(2)` (`DataError`) avant le CHECK : le test accepte les deux erreurs de base.
6. Ruff (lignes, syntaxe générique PEP 695) et mypy (typage des gestionnaires) : corrigés.

## 8. Limites restantes

- **RLS non encore en place** (P2.6) : l'isolation est applicative ; `_base_manager`, du SQL brut ou un `PlatformScope`
  construit à la main la contourneraient. P2.6 ajoutera `SET LOCAL app.current_org` dans `tenant_context` et les politiques
  sur les tables organisationnelles, ainsi qu'une connexion de test sous `rbi_app`.
- Middleware inactif tant que l'authentification n'existe pas (P2.5) ; aucune API exposée (P2.8).
- Requêtes sur `User` non cloisonnées par organisme (gestion des utilisateurs : P2.4) ; rôles RBI absents (P2.4).
- Audit en journal applicatif uniquement (append-only en P2.7) ; `logo` et `document` en attente du stockage applicatif.
- Accès sous mandat du Super Administrateur (§19.2) non implémenté.

## 9. Compatibilité avec la suite

- **P2.4** : `manage_organizations` sera rattachée au rôle SUPER_ADMIN ; l'activation exigera un premier Administrateur institutionnel.
- **P2.5** : placer `SessionMiddleware` + `AuthenticationMiddleware` avant `TenantContextMiddleware` ; un organisme
  SUSPENDU bloque déjà le contexte (connexions bloquées).
- **P2.6** : point d'insertion unique (`tenant_context`) pour `SET LOCAL` ; `TenantScopedModel` identifie les tables à protéger.

## 11. Limites de l'isolation jusqu'à P2.6

**Le RLS métier n'est pas implémenté.** L'isolation entre organismes repose aujourd'hui sur les niveaux 1 à 3
du §12.3 (identité, contexte applicatif, gestionnaires filtrants), pas sur le niveau base de données.

Ce qui est garanti, et testé, tant que le code passe par les mécanismes prévus :
- pas de contexte : aucune lecture ni écriture de données organisationnelles ;
- un organisme ne lit, ne modifie ni ne supprime que ses lignes ; un identifiant étranger équivaut à un identifiant inexistant ;
- le contexte vient du serveur, jamais d'un paramètre client ; les opérations globales passent par une porte auditée.

Ce qui n'est **pas** garanti avant P2.6 :
1. **SQL brut** (`connection.cursor()`, `.raw()`, `.extra()`) : aucun filtrage par organisme.
2. **`Model._base_manager`** et les accès internes de Django : non filtrés. Ils ne sont réservés au cadre que par convention.
3. **Un `PlatformScope` construit à la main** passerait `require_scope` : la garde vérifie le type, pas l'origine.
4. **Le rôle `rbi_app` peut lire toutes les lignes de toutes les tables** au niveau PostgreSQL : un défaut applicatif,
   une injection SQL ou un outil connecté avec ce rôle verrait tous les organismes.
5. **`Organization`, `User`, `AccessRequest` ne sont pas des modèles organisationnels filtrés** : leur cloisonnement
   relève des services (plateforme) et de P2.4 (gestion des utilisateurs par organisme).
6. **Middleware inactif** tant que l'authentification n'existe pas (P2.5) ; aucune API n'est exposée (P2.8), donc
   aucune surface HTTP de données organisationnelles n'existe encore.
7. **Audit** en journal applicatif seulement (append-only en P2.7).

Ce que P2.6 apportera : `ENABLE` + `FORCE ROW LEVEL SECURITY` et politiques `USING` / `WITH CHECK` sur
`app.current_org` pour chaque table `TenantScopedModel` ; `SET LOCAL` dans `tenant_context`, à l'intérieur d'une
transaction ; tests d'isolation exécutés **sous `rbi_app`**, y compris en SQL brut, pour démontrer les points 1, 2 et 4.
