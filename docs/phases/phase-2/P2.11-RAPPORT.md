## 3. Gardes-fous et comportement

Ordre d'exécution : (1) `RBI_ENV` ∈ {`development`, `test`} ; (2) rôle de base = rôle applicatif ; (3) acteur existant,
actif, Super Administrateur ; (4) planification en lecture seule, toute collision refuse le lot ; (5) application dans
une seule transaction.

- Toute collision (organisme ou compte homonyme sans marqueur, compte hors du jeu, rôles différents, organisme dans un
  état inattendu) refuse le lot **sans aucune écriture ni modification**.
- Une erreur pendant l'application annule tout le lot. Message utilisateur sans détail interne ; détail dans les
  journaux serveur.
- Les succès d'audit sont écrits au commit : un lot annulé ne laisse aucun succès, mais les refus restent journalisés.
- Idempotence : une seconde exécution ne crée rien et ne modifie rien ; les éléments existants sont signalés comme
  « déjà présents ».

## 5. Activation des comptes (procédure manuelle)

La commande ne déclenche pas la réinitialisation : le parcours existant exige une requête HTTP (limitation par adresse
et journal d'audit), qu'un outil de ligne de commande ne peut pas fournir proprement. Procédure, en développement :

1. Ouvrir `http://127.0.0.1:8080/connexion`, puis « Mot de passe oublié ».
2. Saisir l'adresse du compte (par exemple `admin@demo-a.rbi.test`).
3. Ouvrir la messagerie de développement `http://127.0.0.1:8025` et suivre le lien reçu.
4. Définir un mot de passe, puis enrôler la MFA à la première connexion (exigée pour les rôles concernés).
5. Pour `AGENT` et `ANALYST`, dont la MFA n'est pas obligatoire : l'activer volontairement depuis la page Profil, afin
   que chaque compte de démonstration dispose de la MFA (§26). Étape non vérifiée de bout en bout.

Aucun mot de passe n'est fourni par le dépôt.

### 5.1 État de vérification de la procédure

- **Vérifié, par la suite E2E de P2.10** (`frontend/e2e-integrated/integrated.spec.ts`, tests 3 à 7) : l'administrateur
  institutionnel créé par le service métier reçoit le lien de réinitialisation dans Mailpit, définit son mot de
  passe, puis enrôle la MFA et se connecte. Ce mécanisme est celui de la procédure ci-dessus.
- **Non vérifié pour les comptes de démonstration** : aucun compte DEMO n'existe (aucune exécution réelle de la
  commande) ; la vérification de la connexion et des permissions de chacun des cinq rôles reste à faire après

- **Non vérifié** : la réception du lien pour un compte `.test` particulier, et l'enrôlement MFA des rôles qui ne
  l'exigent pas (AGENT, ANALYST).

### 10.3 Lacunes trouvées et corrigées dans le périmètre autorisé

1. **CP-07 non détectée (lacune)** : la suite ne vérifiait l'isolation que par le chemin normal, où la RLS masque les
   comptes de B. Un test dédié (`test_application_filter_isolates_without_rls`) exécute le même sélecteur en rôle
   propriétaire, RLS contournée, comme le test P2.10 : seul le filtre applicatif peut alors protéger B. Après ajout,
   la mutation est détectée.
2. **CP-04b détectée seulement par le message (lacune)** : le compte hors jeu n'avait aucun rôle ; un second contrôle
   (rôles différents) le refusait aussi, et le test ne vérifiait que le message. Le compte porte désormais le rôle
   `ORG_ADMIN` attendu : seule la collision peut refuser le lot. Sous mutation, le lot n'est plus refusé mais échoue
   par la contrainte d'unicité, puis est annulé.
3. **Lacune restante, documentée** : CP-05 est détectée par quatre tests, mais le test de secret échoue par un chemin
   indirect. Aucune donnée n'est affectée : il s'agit d'un défaut de précision du test, sans conséquence sur la
   détection.

Les tests ajoutés ou renforcés sont les deux seuls changements du fichier `test_seed_demo.py` depuis la validation
du périmètre. Les empreintes de `demo.py`, `seed_demo.py` et `selectors.py` sont identiques à l'état initial.

### 10.4 Événements d'audit après un échec (CP-06)

- Un succès dans une transaction est écrit au commit. Un lot annulé par une erreur ne laisse donc **aucun** succès
  d'audit. Le test vérifie l'absence de `organization.register` en succès après l'erreur.
- Un refus (`denied`) est écrit immédiatement et persiste même si le lot est annulé. C'est un comportement voulu :
  une tentative refusée reste traçable.
- Sous mutation (sans transaction), les écritures déjà validées restent, et leurs succès d'audit aussi : c'est
  précisément le risque que CP-06 démontre.
